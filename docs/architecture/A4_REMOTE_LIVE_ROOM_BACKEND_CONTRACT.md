# A4-001B — Remote LiveRoom backend contract

## Purpose

A4-001B introduces the first remote backend for ephemeral multiplayer rooms without changing the existing local learner `StudentSession` or the legacy result `idSesion`.

The new remote aggregate is `LiveRoom`.

A `LiveRoom` references one immutable publication by `campaignId + publicationId`. The publication remains persistent. The room is ephemeral.

## Lifecycle rule

The authoritative idle timeout is 600000 ms (10 minutes).

The server owns all room timestamps.

- At exactly `expiresAt`, the room is still active.
- When server time is greater than `expiresAt`, the room is expired.
- A join or heartbeat before or exactly at the boundary refreshes `lastActivityAt` and derives a new `expiresAt` exactly 10 minutes later.
- A request arriving after the boundary cannot reactivate the room.
- Access to an expired room returns `ROOM_EXPIRED` with the user-facing message `Esta sesión finalizó por inactividad.`

Physical deletion is intentionally deferred. Semantic expiration is immediate; later cleanup may remove expired rows without changing the contract.

## Remote operations

Protocol version: `1.0`.

Dedicated POST envelope:

`{ liveRoomRequest: <request> }`

The envelope is deliberately disjoint from publication `{ request: ... }` and legacy learner-result payloads.

Supported operations:

- `createLiveRoom`
- `joinLiveRoom`
- `heartbeatLiveRoom`
- `getLiveRoom`

No delete, reopen or reactivate operation exists.

## Create

`createLiveRoom` receives:

- `campaignId`
- `publicationId`
- `participantId`
- `capabilityToken`

The backend verifies that the exact immutable publication exists and that the campaign identity matches. The backend generates `roomId` and all timestamps. The creator is registered as role `host`.

## Join

`joinLiveRoom` receives:

- `roomId`
- `participantId`
- `capabilityToken`

A successful join registers role `player` and counts as room activity. The initial contract caps one room at 64 total presences including the host.

## Heartbeat

`heartbeatLiveRoom` receives:

- `roomId`
- `participantId`
- `capabilityToken`

The participant capability must match the stored SHA-256 hash. A valid heartbeat updates both participant `lastSeenAt` and room `lastActivityAt` using server time.

The capability is an internal per-participant credential generated by the client. It is not a teacher password, account credential or user-entered key.

## Read

`getLiveRoom` receives only `roomId` and never extends activity. Reading a room therefore cannot keep it alive.

## Secret boundary

`LiveRoom` and presence snapshots contain no capability token and no capability hash.

Only the SHA-256 capability hash is persisted in the presence sheet. Plaintext capability tokens are never written to Sheets or returned inside room/presence snapshots.

## Idempotency

Successful mutating requests are recorded by `requestId + requestHash` in `CRIOS_SALA_SOLICITUDES`.

Replaying the exact request returns its original data without duplicating rooms, presences or heartbeats. Reusing the same `requestId` with a different request returns `REQUEST_CONFLICT`.

## Storage

New sheets:

- `CRIOS_SALAS`
- `CRIOS_SALA_PRESENCIAS`
- `CRIOS_SALA_SOLICITUDES`

Publication sheets are not changed.

## Existing concepts left unchanged

A4-001B does not modify:

- `StudentSession` and local learner progress;
- legacy result `idSesion`;
- publication lifetime or publication storage;
- Studio;
- Runtime UI;
- mission state;
- teacher accounts or teacher keys.

## Transport compatibility

`Code.gs` detects the dedicated LiveRoom POST envelope before publication and legacy learner-result handling.

Publication POST routing and legacy result POST routing remain available.

## Validation

The focal backend regression covers:

- exact 10-minute boundary;
- server-authoritative clock;
- publication reference validation;
- server-generated room identity;
- host/player presence;
- join and heartbeat activity;
- expiration and non-reactivation;
- capability validation and hash-only storage;
- request replay and conflicts;
- 64-participant cap;
- formula-safe spreadsheet values;
- dedicated transport routing;
- preservation of publication and legacy result routes.

## Next boundary
