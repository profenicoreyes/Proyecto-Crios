# A3-003B7D1 — Anonymous create-only publication backend

## Product decision

CRIOS publication sharing must not require a teacher password in the normal flow.

The public remote write boundary is therefore reduced to one operation: creating a new immutable publication. Reads remain public and exact by `campaignId + publicationId`. Mutable activation/deactivation operations remain retired.

## B7D1 scope

B7D1 changes the backend boundary first so frontend and backend can be deployed safely in sequence.

The backend accepts both POST envelope shapes during rollout:

- `{ request }` — final anonymous form;
- `{ request, writeToken }` — transitional compatibility with the previously deployed client. The token is ignored.

Teacher authorization no longer gates `publishPublication`.

The frontend still prompts for the teacher key until B7D2. This temporary asymmetry is intentional: deploy B7D1 backend first, then B7D2 frontend, avoiding a window where the new frontend talks to an old token-required backend.

## Create-only safety boundary

Anonymous publication is constrained by all of the following:

- only `publishPublication` and exact immutable `getPublication` are enabled remotely;
- publication payload shape is strict and dangerous object keys are rejected;
- content remains capped at 524288 UTF-8 bytes;
- the server recalculates and verifies SHA-256 before storage;
- `publicationId` is generated by the server and cannot be supplied by the caller;
- versions are assigned by the server;
- request IDs remain idempotent and conflicting reuse is rejected;
- mutable activate/deactivate requests are rejected before locks or writes;
- new anonymous publications are globally limited to 30 per 60-second window;
- storage is capped at 5000 publication records;
- idempotent replay is allowed even when the new-write rate limit is reached;
- legacy CRIOS results POST handling remains separate and unchanged.

The rate limit is deployment-global because Google Apps Script does not expose a trustworthy caller IP at this boundary. It is an abuse brake, not user authentication.

## Transitional compatibility

`WRITE_UNAUTHORIZED` remains in the wire error-code vocabulary for one transitional period so a frontend/backend version mismatch can still parse an older deployed backend response. The B7D1 backend itself no longer emits that error for publication.

The legacy teacher-auth helper remains physically present but is unreachable from the normal publication request path. Physical dead-code cleanup is deferred until the password-free flow is fully validated and deployed.

## Rollout order

1. Commit and deploy the B7D1 Apps Script backend.
2. Confirm anonymous request-only publication works against the deployed endpoint.
3. Apply B7D2 to remove teacher-key handling from Studio/client.
4. Validate the complete password-free flow.

## Rollback

Before commit, restore the five pre-B7D1 files from the external rollback folder and remove this document.

After commit, revert B7D1 as one unit. During the transition, the old frontend remains compatible because B7D1 still accepts its legacy envelope shape.
